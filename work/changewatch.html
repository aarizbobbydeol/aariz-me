One bad deploy, start to finish

Recorded from a real run of ChangeWatch with its demo shop: a healthy deploy, a bad one, then the fix. To keep it short, the checks ran at 2 and 4 minutes after each deploy instead of the usual 10 and 30.

kim@demo-shop pushes “Apply discount to totals”. The deploy hook sends the commit, the diff and the CODEOWNERS file. Line 42 of app/billing.py now divides by order.discount, which is often zero.

The first error arrives 1 second after the deploy. Nine seconds later the team gets the alert: the failing line, that this release changed it, and who owns it.

⚠️ Possible regression: ZeroDivisionError: division by zero (7x) at app/billing.py:42 (this line was changed in this release) after deploy 51afe8f3 by kim@demo-shop.example. Owners: @demo-shop/payments.

After 13 errors the incident is confirmed. Its page shows the changed line, the owners, the timeline and the exact commands to undo the deploy.

At the first check, fixed rules give the verdict: ROLLBACK, because one new error type appeared. The risk review had already flagged the line as dividing by a value that may be zero.

The fix reverts the line. Its verdict comes back SAFE, and 7 minutes 21 seconds after the bad deploy the incident resolves itself, noting it was likely reverted by the fix.

The problem

Small Python teams often can't tell quickly whether a deploy caused new errors. Full monitoring suites cost money and send code and error data to someone else's servers.

ChangeWatch runs on the team's own server. It watches errors and traffic after every deploy, alerts within seconds when something new breaks, and gives each release a verdict, naming the likely file, line and owner.

How it works

  1. DeployA GitHub Action sends the commit, a size-capped diff with secret files left out, and the CODEOWNERS file. It only reads the repo, and it never fails the pipeline.
  2. ObserveA dependency-free Python SDK reports exceptions, slow requests and request counts. It strips secrets and emails before anything leaves the app.
  3. StoreEvents go onto a Redis queue. A worker writes each batch to Postgres in one transaction: duplicates removed, errors grouped into issues, stack traces encrypted.
  4. AlertA new error seen three or more times within a minute of a deploy opens an incident. The alert is saved in the same transaction and sent to Slack, Discord, Teams, email or a webhook within about a second.
  5. ExplainThe investigator gathers the diff near the failing line, the failed requests and similar past incidents, asks Claude or a local Ollama model for the likely cause, and checks the answer against that evidence.
  6. VerdictFixed rules compare error rates before and after the deploy and give a verdict at 10 minutes and again at 30: safe, watch, rollback, or no data.

Decisions I made

  • Rules decide the verdict, not the AI. The model only explains the cause, and AI budgets can pause explanations but never verdicts or alerts.
  • Each alert is written to an outbox in the same database transaction as its incident, so a worker crash or a Slack outage can't lose an alert or send it twice.
  • It never writes to a team's code. The one exception is an opt-in draft pull request that undoes a deploy, and CI scans the code to keep it that way.
  • Each project gets a separate manage key, so the read key that sits in dashboards and AI tools can't mute alerts or raise the AI budget.

Released

v1.0.2 ships as multi-architecture Docker images and as the changewatcher package on PyPI. A one-command installer sets up HTTPS, fresh secrets and a first project, and CI tests it on new Ubuntu servers (Intel and ARM) on every change. The SDK works with FastAPI, Django and Flask, tested on Python 3.9 to 3.14.
